# Гайд: как работать с Claude по RIFFA без потерь

Это твоя шпаргалка + моя памятка для всех будущих сессий. Открывай при необходимости.

---

## 🎯 Главный принцип

**Ты — продакт-менеджер, Claude — исполнитель.**  
Я не должен решать стратегически. Я должен:
1. Предложить план
2. Дождаться одобрения
3. Сделать
4. Показать результат
5. Ждать следующей задачи

Если я начинаю «активничать» без плана — **останови меня**. Это плохой знак.

## 🚨 Стоп-фразы (запоминай, используй смело)

| Фраза | Что делает |
|---|---|
| **«Стоп, не торопись»** | Я останавливаюсь, отчитываюсь о состоянии, жду указаний |
| **«Сначала план»** | Я не пишу код, а описываю что собираюсь сделать |
| **«Покажи diff перед коммитом»** | Я не коммичу пока не одобришь |
| **«Не трогай прод»** | Я не работаю в `/root/frontend/` и не деплою в `/root/backend/static_dist/` |
| **«Закоммить и запушь сейчас»** | Я фиксирую промежуточный результат в git |
| **«Проверь git status»** | Я показываю что не сохранено |

## ⚠️ Опасные операции — всегда подтверждение

Я **обязан спросить тебя** перед:

- `git checkout <branch>` / `git switch` (особенно если в working tree есть изменения)
- `git reset --hard` / `git push --force`
- `git rebase`
- `rm -rf` / `find ... -delete`
- Деплой на прод (любая операция с `/root/backend/static_dist/`)
- Перезапуск backend в Docker (`docker compose restart`)
- Изменения в `nginx`, `systemd`, `.env` файлах
- Что-либо в БД (миграции, DROP TABLE, UPDATE без WHERE)
- Force push в `main`

Если я делаю это без согласования — **это мой косяк, скажи и я остановлюсь.**

## 💾 Сохранение работы — план «никогда не теряем»

### Уровень 1: Git (главное)
**Правило: каждая логическая задача = отдельный коммит.**
Не копи правки часами без коммита. После каждой завершённой подзадачи говори: «закоммить».

После сессии (или в её середине) проси:
> Закоммить и запушь всё что сделано в ветку X. Покажи git log -3 чтобы убедиться.

### Уровень 2: Файлы-планы в репо
Всё что хочешь чтобы я помнил между сессиями — пиши в `.md` файл в репо:
- `REDESIGN-PLAN.md` — план редизайна
- `GUIDE.md` — этот файл
- `TODO.md` — текущие задачи
- `DECISIONS.md` — почему выбрали X а не Y

Эти файлы я читаю по запросу. **Они всегда актуальнее моей внутренней памяти.**

### Уровень 3: Memory (`~/.claude/projects/-root/memory/`)
Долговременная память, которая автоматически загружается в начале каждой сессии. Я туда сам пишу важное (профиль проекта, обратную связь, ключевые ссылки).

**Тебе вмешиваться обычно не нужно** — я сам поддерживаю. Если хочешь зафиксировать факт:
> Запомни это: <факт>. Сохрани в memory.

### Уровень 4: Прототипы / макеты
HTML-прототипы, скриншоты, дизайн-гайды — всегда сохраняй в репо:
- `/frontend/public/prototype.html` — будет доступен на сайте
- `/docs/design/` — для статичных макетов и описаний

**Никогда** не оставляй в `/tmp/` — там пропадёт.

## 🌳 Структура веток RIFFA (запомни)

| Ветка | Где работает | Когда трогать |
|---|---|---|
| `main` | https://riffastudio.site (прод) | только когда фича готова, проверена на beta, и ты явно говоришь «деплой на прод» |
| `design-v3` | https://beta.riffastudio.site | редизайн, эксперименты, всё связанное с v3 |
| `recovery-fixes` | (не задеплоено) | бэкап — все недельные фиксы которые ещё не интегрированы на прод |

**Worktree-каталоги:**
- `/root/frontend/` — main (прод)
- `/root/frontend-beta/` — design-v3 (beta)
- НИКОГДА не делать `git checkout` или `git switch` в `/root/frontend/`

## 📐 Workflow для дизайна (после сегодняшних ошибок)

1. **Прототип сначала** — HTML или скриншот, который ты одобряешь
2. **План перед кодом** — какие файлы, какие компоненты, какие риски
3. **Только в beta** — никогда не трогаем прод во время дизайн-работы
4. **Коммит после каждого экрана** — не накапливать
5. **Скриншот результата** перед тем как «закончить»
6. **Перенос на прод — отдельная задача**, не «заодно»

---

## 🔄 Workflow для разработки (фиксы / новые фичи)

1. **Сначала на main** (или feature ветку) — потому что фиксы должны быть в проде
2. **Коммит каждые 30-60 минут** работы или после каждой фичи
3. **Push на GitHub** хотя бы раз в день
4. **Если ветка `recovery-fixes` непуста** — сначала разобраться с ней, потом новые фичи

## 📝 Конец каждой сессии — обязательный чек-лист

Перед тем как закрыть сессию, проси:

```
1. git status — что не закоммичено?
2. git log -5 на текущей ветке
3. Запиши в REDESIGN-PLAN.md (или другой файл) что сделано и что осталось
4. Закоммить и запушь всё
5. Обнови memory если есть новые важные факты
```

Если хочешь супер-короткий вариант:
> Подведи итоги сессии и сохрани всё.

## 🆘 Если что-то пошло не так

### «Я не понимаю что произошло»
> Не делай ничего. Подробно объясни простыми словами что случилось, шаг за шагом. Где сейчас прод, где beta, что в working tree, что в каждой ветке.

### «Откатить хочу»
> НЕ делай git reset. Сначала покажи git reflog, git stash list, untracked files. Я хочу понять что у нас есть прежде чем выбирать стратегию.

### «Сайт сломался»
> Открой /health на проде. Если backend жив — проблема во фронте, верни последний рабочий билд из git. Если backend мёртв — посмотри docker logs.
