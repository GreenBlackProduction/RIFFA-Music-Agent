# Перестройка промт-пайплайна (начато 2026-08-13)

Причина: пользователь просил «таинственное техно только с синтезаторами, без ударных,
бита и бочки, средний темп, тревожное настроение». Несколько итераций через агента и
через форму дали агрессивный электронный хип-хоп/дабстеп. Тот же смысл, введённый
руками в оригинальную Suno, дал нужный результат с первой попытки.

## Принцип

**Описание пользователя — это спецификация. Обогащение имеет право заполнять пробелы
и не имеет права спорить.**

Сейчас наоборот: описание — одна из подсказок, а спецификацией де-факто работает
пресет жанра.

## Диагноз (что нашли в коде и логах)

- `SongParams.user_description` объявлен и **нигде не используется** в `build_suno_style`.
- `_style_head_text` выбрасывает кириллицу целиком → русский бриф не попадает в
  детерминированный стиль вообще, только в GPT-обогатитель.
- `_ensure_rich_style` отбрасывает ответ GPT, если он короче `max(240, 60% пресета)` —
  простой точный запрос заменяется пресет-салатом.
- Системный промт обогатителя (`_SYS_ENRICH_MUSIC`) обязывает раздувать короткий
  запрос до 500–1200 символов и запрещает писать отрицания в тексте.
- Канал исключений (`negativeTags`) собирается только из `style_prompt` и
  `constraints`; `description` туда не попадает → «без ударных» теряется в обоих
  каналах сразу.
- Фрагменты пресета семплируются случайно → слово жанра выживает не всегда
  (у `Techno` 7 фрагментов, при «богатом» брифе берётся 4).
- Пресет и профиль темпа дают два разных BPM в одном промте.
- Случайная «соль» подмешивает чужие жанровые токены (`melismatic R&B runs`,
  `gravelly blues rasp`) в инструментал; фильтр вокальных фраз их не ловит.
- `agent_music_params` пуст в **20 генерациях из 20** за месяц — ветка «богатого
  брифа» (инструменты, техники, ограничения агента) фактически мертва.

### Решения владельца (2026-08-13)

* **Финальный промт пользователю не показываем** — его могут скопировать для
  обучения чужих агентов или прямого использования в Suno. Показывать можно
  только «основу» — разбор брифа (`ParsedBrief.locked_summary()`), чтобы
  человек видел направление: `Techno; +synthesizers; −drums, kick, beat;
  medium tempo; anxious`.
* **`agent_music_params` в новой архитектуре почти не нужен**: парсер и так
  читает свободный текст. Канал остаётся оправдан только для фактов, которых в
  словах пользователя не было, а агент их нашёл (эпоха, BPM, инструментарий
  референса из Deezer / Last.fm). Фаза 5 = отдавать эти факты в структуре
  парсера, остальное поле выбросить.

## Выводы фазы 0

1. **Канал исключений не работает** — 1 успех из 21. Самый дешёвый и самый ценный фикс.
2. **Пайплайн бимодален.** Когда ответ GPT выживает — ~89%. Когда его отбрасывает
   порог длины — ~80% и вдвое больше критических провалов. В проде 12.08 несколько
   payload'ов ушли чистым пресет-салатом, то есть плохой режим реален, а не теоретичен.
3. **Случайность — не украшение, а дефект.** Один бриф даёт от 57% до 100%.
4. GPT-обогатитель справляется лучше, чем предполагалось: губит его окружение
   (порог длины, обрезка 1687→988 символов, неподключённый канал исключений).

## Фаза 1a — исключения из описания (2026-08-13)

Правка: `extract_negative_tags()` в `prompt_engineering.py` + один вызов в
`build_suno_style`. Существующая `extract_negatives` не тронута (она переписывает
текст, поэтому обязана останавливаться на первой запятой; новая функция отдаёт
только теги и потому читает всё перечисление). Тесты: `tests/test_prompt_negatives.py`,
10 штук.

Сравнение на **одинаковом сиде** (`--seed 42`, только сборщик, без GPT):

| Проверка | до | после |
|---|---|---|
| средняя верность | 79% | **83%** |
| `forbidden_tagged` | 0% (0/21) | **71%** (15/21) |
| `forbidden_absent` | 67% (14/21) | **71%** (15/21) |
| `bpm_single` / `required_present` / `genre_anchor` / `no_cross_genre_salt` | 64 / 76 / 93 / 75% | без изменений |

Все несвязанные проверки совпали до последнего прогона — правка хирургическая.

Полный пайплайн (с GPT, 3 прогона, без сида — GPT остаётся источником шума):
на 7 брифах с исключениями средняя выросла **81.7% → 89.4%**; общее среднее по
всем 16 брифам сдвинулось 89% → 88%, то есть в пределах шума, потому что 9 из 16
брифов правка не затрагивает вообще, а разброс на них ±10 пунктов.

Оставшиеся провалы `forbidden_tagged` (6 из 21) — брифы `news-synth-only` и
`trap-drums-only` с формулировкой «без дополнительных инструментов»: система ставит
честный тег `additional instruments`, а разметка ждёт список из пяти конкретных
инструментов. Развернуть «единственный инструмент — синтезатор» в явные запреты —
задача парсера фазы 1, не регулярки.

**Методический вывод:** без `--seed` сравнения бессмысленны — один и тот же бриф
даёт от 38% до 100%. Все дальнейшие замеры делать с сидом, а по GPT-пути сравнивать
только затронутые брифы.

## Фаза 3 — композитор и валидатор в бою (2026-08-13)

`app/services/prompt_pipeline.py` — **единственная точка входа**:
`build_suno_prompt(description, genre, mood, tempo, instrumental, ...)`.

```
понять (1) → заполнить пробелы (2) → собрать (3) → проверить
                                                    ↙        ↘
                                            принять/починить  откат
```

Композитор получает `LOCKED` / `OPEN` / `EXCLUDED` и может только
формулировать; длина ответа следует брифу, а не цели («150-350 символов —
правильный ответ, а не ленивый»). Дальше готовый текст проверяется
`check_faithfulness` **до отправки в Suno**, причём критерием служит разбор
самого брифа (в бою человеческой разметки нет — контрактом становятся поля
`locked`). При критическом провале даётся одна попытка починки со списком
конкретных нарушений; если и она не проходит — отправляется детерминированный
рендер этапа 2, который не может противоречить брифу, потому что только
склеивает уже одобренный материал.

Без доступного провайдера весь пайплайн работает детерминированно и бесплатно.

Тесты: `tests/test_prompt_pipeline.py` (5 штук) — приём верной композиции,
починка при протаскивании запрещённого инструмента, откат при повторном
провале, детерминированный путь без клиента, состав запроса к композитору.

## Фаза 6 — подключение к воркеру (код готов, НЕ задеплоено)

Флаг `settings.prompt_pipeline` (`PROMPT_PIPELINE`), по умолчанию `old`.

Три ветки воркера (`song`, `instrumental`, `occasion`) собирали стиль тремя
почти одинаковыми копиями кода. Теперь у них одна общая функция
`_build_style_payload()` в `app/tasks/__init__.py`, внутри которой живут оба
пути. Ветка `cover` не тронута.

Payload-дамп и лог теперь пишут `pipeline`, `source`, `faithfulness` и
`understood` — по логам видно, что система поняла и насколько промт этому
соответствует, без запуска dry-run.

Нет ни одного провайдера в конфиге → новый путь работает детерминированно,
а не роняет генерацию.

Тесты: `tests/test_worker_style_payload.py` — флаг `old` зовёт обогатитель,
флаг `new` его не трогает и отдаёт мета-поля.

### Две мелкие разницы легаси-пути после объединения

* инструментал теперь передаёт обогатителю `agent_research_notes` (раньше не
  передавал; на практике поле пустое в 20 генерациях из 20);
* `occasion` получил фолбэк `params["custom_genre"]`, которого у него не было.

### Как выкатывать

```bash
# 1. пересобрать образ воркера (флаг по умолчанию old — поведение не меняется)
cd /root/backend && docker compose build worker && docker compose up -d worker
# 2. включить новый путь
#    PROMPT_PIPELINE=new в .env, затем
docker compose up -d worker
# 3. откат — вернуть PROMPT_PIPELINE=old и перезапустить
```

Контрольная проверка после включения: сгенерировать вчерашний бриф
(«таинственное техно только с синтезаторами, без ударных, бита и бочки»),
посмотреть `SUNO PAYLOAD` в логах воркера — там должны быть `pipeline=new`,
короткий стиль и `negativeTags` с drums/beat/kick.

## Инцидент 2026-08-13: исчерпана квота GPT

~112 вызовов gpt-4o с `max_tokens=1500` (замеры baseline и после фазы 1a)
исчерпали баланс ключа `APIYI_KEY`. Симптом: `403 insufficient_user_quota`
при любом вызове, резервирующем ~11.5k единиц квоты; мелкие вызовы проходят.

Последствия для прода: инструментал деградирует на пресет-путь, песня с
AI-текстом падает (`generate_lyrics` пробрасывает исключение).

**Запасного ключа нет:** `make_lyrics_client` берёт `apiyi_key or openai_api_key`,
а `OPENAI_API_KEY` в `.env` невалиден (прямая проверка → `401 Incorrect API key`).
Весь сервис висит на одном балансе одного прокси.
